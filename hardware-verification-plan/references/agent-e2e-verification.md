# AI 에이전트 E2E 설계 세션 검증

이 문서는 AI 에이전트가 CAD·해석 도구를 호출해 "설계했다/검증했다"고 보고하는 제품을, **산출물과 세션 양쪽에서** 검증하는 절차다. SKILL.md 13단계의 상세판이다. 도구 이름은 제품마다 다르므로 이름이 아니라 역할로 대응시킨다.

## 0. 언제 쓰나

- AI CAD 에이전트가 "링키지 설계 완료", "간섭 없음", "강도 검증 완료"라고 보고한다.
- 에이전트가 만든 형상은 있지만, 어떤 도구를 어떤 경계에서 호출했는지 모른다.
- 에이전트의 도구 호출 로그는 성공인데 실제 형상·치수·운동이 요구와 다르다.
- 제품의 시스템 프롬프트·JIT 스킬·서브에이전트 구조가 설계 판정에 어떤 영향을 주는지 감사해야 한다.
- "모델이 알아서 검증했다"는 주장을 독립 오라클로 확인해야 한다.

이 모드는 설계 자체를 대신하지 않는다. 기존 L0–L5 오라클과 함께, **세션 계약 → 실행 경계 → 산출물**을 연결하는 층을 추가한다.

## 1. 세 축을 분리한다

| 축 | 답하는 질문 | 대표 증거 | 이 증거가 답하지 않는 것 |
| --- | --- | --- | --- |
| 세션 계약 | 모델이 무엇을 받고 시작했나 | 모델·effort·permission, 도구 목록, 지침 해시, JIT 스킬 | 모델이 실제로 그 지침을 지켰는가 |
| 실행 경계 | 어떤 호출이 어디서 실행됐나 | 호출 이름·인자·결과, 로컬/원격/호스트, 세션·이벤트 ID | 형상이 요구를 만족하는가 |
| 산출물 | 실제 형상·파일이 요구를 만족하나 | CAD 파일 해시, 독립 오라클, 전 행정 검사, FE/MFBD | 어떤 요청·모델·경로에서 나왔는가 |

세 축은 **세션 ID와 산출물 SHA-256**으로 연결한다. 도구 호출 로그만 있으면 "무엇을 만들었는지"를 모르고, 형상만 있으면 "어떻게 만들어졌는지"를 모른다. 둘 다 있어야 "이 에이전트가 이 요청에서 이 설계를 했고, 이 설계가 요구를 만족한다"고 말할 수 있다.

## 2. 정적 복원

소스·설치본을 읽을 수 있으면 모델을 실행하기 전에 아래를 표로 만든다. 각 행은 **소스 경로:줄**과 **확인/미확인**을 붙인다.

| 항목 | 확인할 것 | 흔한 실패 |
| --- | --- | --- |
| 진입점 | 모델 루프를 소유한 프로세스, 도구를 실행하는 프로세스 | 데스크톱 UI가 모델을 직접 부른다고 오해 |
| 세션 봉투 | 기본 모델·effort·permission, 모델 선택지, 도구 수, 호스트 도구 | UI 표시와 실제 세션 설정이 다름 |
| 지침 | 시스템 지침 길이·해시, 조건부 삽입, 언어·환경 블록 | 지침 전체를 한 파일로 오해 |
| 스킬 | JIT 스킬 목록, 라우트 조건, 스킬이 바꾸는 도구 순서 | 스킬을 단순 도움말로 오해 |
| 실행 경계 | 로컬 CAD, 원격 샌드박스, 호스트, 서브에이전트 | 같은 도구 이름을 같은 실행 위치로 오해 |
| 턴 루프 | 호출·결과·종료·재접속 이벤트, `success`/`idle` 처리 | 턴 종료를 설계 완료로 오해 |
| 주장 경로 | 에이전트가 "검증"의 근거로 쓰는 필드 | 후보 점수·미리보기·재생을 오라클로 오해 |

### 2.1 세션 봉투

기록할 값:

- 모델 식별자와 기본값, effort/추론 강도, permission 모드.
- 모델 선택지 수와 각 선택지의 이름. 선택지가 달라도 방법론은 같을 수 있지만, 추론 능력과 도구 호출 성향은 달라진다.
- 기본 MCP 도구 수, 조건부 도구, 호스트 도구, 외부 MCP 등록 수.
- 시스템 지침의 문자 수와 해시. 조건부 환경 변수로 지침이 바뀌면 on/off를 따로 기록한다.
- JIT 스킬 수와 이름, 각 스킬의 라우트 조건.
- 서브에이전트 종류·예산·모델·금지 작업.

```text
session:
  default_model: <id>
  default_effort: <low|medium|high|...>
  permission: <auto|ask|...>
  models: <n>
  mcp_tools: <n>
  host_specs: <n> (external: <n>)
  skills: <n>
  instructions_sha256: <hash>
  instructions_chars: <n>
  subagents: [{type: branch, budget: <n>}, {type: verify, budget: <n>}]
```

### 2.2 도구·스킬 라우팅

- 시스템 지침이 "이 작업을 하기로 정했으면 `skill(name=...)`을 읽어라"처럼 **작업 선택 이후** 스킬을 라우트하는지 본다.
- 스킬이 도구의 순서·판단 기준·금지 사항을 바꾸는지, 아니면 설명만 하는지 확인한다.
- 특정 도구 세트를 우선하라는 허브/카탈로그 규칙이 있으면, 그 규칙이 요구사항을 왜곡할 수 있는지 본다.
- 지침이 "고정된 순서가 아니다"라고 말하는지, 실제로는 스킬이 강제 순서를 만드는지 구분한다.

### 2.3 실행 경계

| 경계 | 확인할 것 | 증거로 쓸 때의 한계 |
| --- | --- | --- |
| 로컬 CAD | CAD 프로세스에서 실행되는 도구, `execute_code` 권한 | CAD 상태·파일은 이 경계 안에서만 유효 |
| 원격 샌드박스 | bash/file/도구 실행자, 반환 경로 | 로컬 경로와 공유되지 않음 |
| 데스크톱 호스트 | PCB/도면 열기, CAD 발견·기동, 질문 카드 | UI 성공은 형상 검증이 아님 |
| 브로커 서브에이전트 | branch/verify, 예산, 결과 전달 형식 | branch 결과는 미검증 후보 |

`execute_code`가 OS 샌드박스라고 가정하지 않는다. CAD 프로세스의 권한으로 코드를 실행하는 구현은 별도 샌드박스가 아니다. 반대로 원격 샌드박스의 파일 경로를 로컬 CAD가 읽을 수 있다고 가정하지 않는다.

### 2.4 턴 루프

- 모델 호출 → 도구 호출 이벤트 → 실행자 → 도구 결과 → 모델 재개 → 종료.
- `success`는 **호출의 성공**이고, `idle`/`end_turn`은 **턴의 종료**다. 어느 것도 설계 요구의 합격이 아니다.
- 응답 유실·재접속 뒤 실행 여부가 불확실한 호출은 재실행하지 말고 상태를 먼저 확인한다.
- 사람에게 묻는 도구는 답이 없을 때 답을 지어내지 않고 만료·취소를 구분해야 한다.

## 3. 라이브 추적 스키마

한 요청을 추적할 때 최소한 아래를 남긴다.

```json
{
  "session_id": "...",
  "request": "...",
  "app_version": "...",
  "source_commit": "...",
  "model": "...",
  "effort": "...",
  "permission": "...",
  "cad": {"kind": "FreeCAD", "version": "..."},
  "events": [
    {"seq": 1, "type": "tool_use", "name": "...", "args_digest": "...",
     "runner": "local|remote|host|subagent", "result_status": "ok|error",
     "artifact": null}
  ],
  "artifact": {"path": "...", "sha256": "...", "export_command": "..."},
  "oracles": [
    {"id": "motion", "command": "...", "status": "PASS", "evidence": "..."}
  ],
  "not_run": ["..."]
}
```

- `args_digest`는 비밀을 피하기 위한 요약이다. 원문 인자가 필요하면 redact해서 별도 보관한다.
- 이벤트 순서는 세션의 실제 순서다. 정적 소스의 도구 목록 순서와 혼동하지 않는다.
- `artifact`는 에이전트가 반환한 경로가 아니라 **실제로 접근해 해시를 잰 파일**이다.
- `oracles`는 이 skill의 독립 검사다. 에이전트가 호출한 도구의 `success`를 여기에 넣지 않는다.

## 4. 게이트 커버리지

도구 이름이 아니라 역할로 채점한다. 각 행은 `PASS`, `FAIL`, `NOT_RUN` 중 하나이고, `PASS`에는 증거 위치가 붙는다.

| 게이트 | 요구 | 통과 증거 | 거짓 통과 |
| --- | --- | --- | --- |
| G0 컨텍스트 | CAD 종류·지원 범위·스크립트 호출법 | 컨텍스트 도구 결과 + 런타임 블록 | 연결 성공 |
| G1 요구 | 치수·포즈·재질·공정·미지수 | 사용자 답·가정·범위표 | 추정으로 채움 |
| G2 방법 | 합성/직접 저작/가져오기 선택 | 선택 이유 + 도구 결과 | 카탈로그에 요구를 맞춤 |
| G3 생성 | 후보 또는 실패 이유, 제약 유지 | 후보 목록·오류·제약 비교 | 후보 수·점수 |
| G4 비교 | 2~3개를 요구와 비교 | 후보별 오차·간섭·운동 범위 | 1등 점수 |
| G5 빌드 | 객체·치수·파일 해시 | `get_objects`/CAD 파일 해시 | 미리보기·재생 |
| G6 운동 | 전 행정·전 위상 | `verdict=clear` + `complete=true` + 검사 범위 | 정지 자세 무간섭 |
| G7 강도 | 형상 입력의 독립 FE/FEM | 수렴·평형·안전율 | 간섭 없음, 두께 추정 |
| G8 제조·도면 | DFM/도면 검사와 수정 | 문제 면·재검사·시트 확인 | STEP/DXF 생성 |
| G9 보고 | 확인/미확인 분리 | 산출물 해시, 판 번호, NOT_RUN | "완료" 문장 |

`G6`은 특히 엄격하다. 정지 자세 하나, 시작 자세 간섭 없음, 애니메이션 재생은 전 행정 검사가 아니다. 검사 도구가 `incomplete`를 반환하면 그 범위는 `NOT_RUN`으로 남긴다.

## 5. 사례: Metheus 1.0.464의 정적 복원

이 사례는 **소스에서 방법론을 복원한 것**이지, 모델이 실제로 그렇게 행동했다는 실행 증거가 아니다. 대상은 로컬 설치본 `1.0.464`다.

### 5.1 확인된 구조

- 모델 루프는 브로커가 소유한다. 로컬 `agent_bridge`는 자식 프로세스로 세션을 열고, `runner=client`인 CAD 도구만 실행한다.
- 로컬 CAD, 원격 샌드박스, 데스크톱 호스트, 브로커 서브에이전트가 분리되어 있다.
- 기본 MCP 도구 74개, 호스트 spec 11개(외부 MCP 등록 7개), JIT 스킬 10개.
- 기본 모델 `openai:gpt-6.1-sol`, effort `medium`, 모델 선택지 12개, MCP instructions 약 10,968자.
- 시스템 지침은 스스로 "고정된 설계 순서가 아니다"라고 말한다. 링키지 합성은 JIT 스킬을 읽은 뒤 문제 정의 → 위상 → 합성 → 후보 → 빌드 → 검증으로 간다.
- `branch`는 최대 3개·250 cents, `verify`는 150 cents다. `branch`는 분석을 하지 않고, `verify`는 요구와 형상만 받는다.

### 5.2 검증에 영향을 준 문장

- "success는 호출의 성공 여부다. error·issues·부분 실패·미검사 항목을 함께 읽는다."
- "높은 점수·미리보기·재생만으로 요구 치수, 운동, 간섭, 하중·강도를 모두 검증했다고 보고하지 않는다."
- "정지 자세 검사만으로 작동한다고 말하지 않는다."
- "간섭이 없다는 것은 강도 검증이 아니다."

이 문장들은 제품이 **도구 성공과 설계 검증을 분리하려는 의도**를 보여 준다. 그러나 실제 모델이 지켰는지는 라이브 추적 없이는 알 수 없다. 실제 검증에서는 4절의 게이트를 추적 로그와 산출물로 채점해야 한다.

### 5.3 이 사례에서 하지 않은 것

- 앱을 실행하거나 모델을 호출하지 않았다.
- CAD 형상을 만들거나 해석하지 않았다.
- 브로커 서버 내부·모델별 도구 호출 정책·안전 필터의 실제 차단 규칙을 확인하지 않았다.
- 모델이 스킬을 읽었는지, 게이트를 지켰는지 관찰하지 않았다.

따라서 결론은 "이 제품은 이렇게 설계하도록 **계약되어 있다**"까지다. "이 제품의 모델은 항상 이렇게 한다"가 아니다.

## 6. 감사표 예시

```text
대상: <제품> <버전> / 소스 <commit>
세션: <id> / <model> / <effort> / <permission>
산출물: <path> SHA-256 <hash> / <export command>
독립 오라클: <command> → <status>

| gate | 기대 | 실제 | 실행자 | 판정 | 증거 |
| G0 | CAD 컨텍스트 | ... | local | PASS | ev:... |
| G1 | 요구 확정 | ... | - | NOT_RUN | 사용자 답 없음 |
| G5 | 빌드 | ... | local | PASS | sha256... |
| G6 | 전 행정 운동 | ... | local | FAIL | incomplete, 40%만 |
| G7 | 강도 | ... | - | NOT_RUN | FE 미실행 |
```

## 7. 판정 문장

- "도구 `build`가 success를 반환했다" → 호출 성공. 설계 합격 아님.
- "세션이 idle로 끝났다" → 턴 종료. 설계 완료 아님.
- "후보 점수가 가장 높다" → 비교 지표. 요구 만족 아님.
- "미리보기/재생이 보인다" → 시각 표본. 전 행정 검증 아님.
- "에이전트가 완료라고 썼다" → 에이전트의 주장. 독립 증거 아님.
- "branch가 결과를 냈다" → 미검증 후보. verify/부모의 판정 아님.
- "원격 샌드박스가 파일을 반환했다" → 그 경계의 산출물. 로컬 CAD에 적용하려면 전송·해시·재검증 필요.

## 8. 한계

- 정적 복원은 세션 계약만 보여 준다. 모델의 실제 준수는 라이브 추적에서만 관찰된다.
- 라이브 추적 한 건은 그 버전·모델·요청·CAD의 증거다. 다른 조건으로 일반화하지 않는다.
- 이벤트 이름과 도구 이름은 제품마다 다르다. 이름이 아니라 역할·산출물로 대응한다.
- 에이전트가 자신의 산출물을 검증하면 독립 검증이 아니다. 가능하면 다른 모델·다른 오라클·사람이 판정한다.
- 추적 로그의 비밀·토큰·개인정보는 redact한다. 원본 접근 권한과 보존 기간을 기록한다.
